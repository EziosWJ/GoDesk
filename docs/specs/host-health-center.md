# Host Health Center（主机健康状态中心）Spec

- 状态：产品方向已确认；本文作为后续实现基线
- 范围：产品规格、交互约定、采集与健康判定设计、HTTP 契约
- 本次变更：仅完善文档，不实现后端采集、健康引擎或前端界面

## 1. 背景与目标

GoDesk 是面向 Linux 主机的 Web 运维桌面。桌面底栏不应复刻 Windows 系统托盘，也不应成为一组缩小的资源仪表盘。它应提供主机健康感知入口，让操作者无需打开系统监控应用，就能判断主机是否存在需要关注的问题。

Host Health Center（主机健康状态中心）负责回答：

1. GoDesk 当前是否仍能连接到被管理主机？
2. 主机整体健康状态如何？
3. 哪些检查项异常，异常持续了多久？
4. 应该进入哪个应用查看详细信息？

核心原则：**底栏展示健康状态，健康中心解释问题，系统监控提供详细指标，服务管理负责服务操作。**

## 2. 产品范围

### 2.1 目标

- 在桌面底栏提供始终可见、低干扰的主机健康状态入口。
- 将 CPU、内存、存储、网络和温度等检查统一聚合为健康状态。
- 区分正常、警告、严重和未知，避免把采集失败或不支持误判为正常。
- 复用现有系统监控采集能力，避免重复采集同一指标。
- 提供稳定、轻量、可扩展的健康状态 API 契约。
- 在不具备传感器或特定系统能力的平台上优雅降级。

### 2.2 非目标

首版不包含：

- 完整监控大屏、长期指标存储、历史趋势报表。
- 邮件、短信、Webhook、桌面推送等通知渠道。
- 自动重启服务、自动清理磁盘或其他自动修复动作。
- 默认探测公共互联网或依赖第三方服务判断主机健康。
- 默认监控主机上的全部 systemd、OpenRC 或 Docker 服务。
- 远程多主机汇聚与集中监控。
- 将浏览器所在设备的电池、音量或 Wi-Fi 状态作为被管理主机状态。

## 3. 信息架构与交互

### 3.1 桌面底栏

底栏继续保留现有应用切换区和时钟。右侧状态区域由主机健康入口替代当前浏览器网络、Web Audio 音量和浏览器电池控件。

常驻内容：

- 主机健康图标与状态文字：正常、警告、严重或未知。
- 存在警告或严重问题时，显示异常数量。
- GoDesk 连接中断时，显示独立的连接状态，不伪装成主机健康结论。
- 本地化时间与日期。

底栏不常驻显示 CPU、内存、磁盘、温度等具体数值。它们属于健康中心和系统监控的详情内容。不得使用 `navigator.onLine`、Web Audio API 或 `navigator.getBattery()` 代替 Linux 主机指标。

### 3.2 健康状态面板

点击底栏主机状态入口，打开轻量面板。面板按以下顺序组织：

1. 整体健康状态、异常数量和最近检查时间。
2. 警告与严重检查项，优先显示异常原因、当前值和阈值。
3. 检查维度摘要：CPU、内存、存储、网络、温度。
4. 可用时显示主机名、运行时间和平台信息。
5. 提供进入「系统监控」查看详细指标的入口。

正常状态下不需要展示大段空白告警列表；可以收起正常检查项，只保留维度摘要。未知状态必须说明数据不可用的原因，不能显示成正常。

面板复用现有任务栏弹出层交互。窄屏下应限制面板宽度和高度、允许内部滚动，并保证状态入口仍可触达；不得通过缩小任务栏按钮命中区换取空间。

### 3.3 状态语义

| 状态 | 含义 | 展示建议 |
| --- | --- | --- |
| `healthy` | 所有适用且已启用的检查均正常 | 中性图标或成功状态，文字「主机正常」 |
| `warning` | 至少一个检查达到警告条件，且没有严重项 | 警告色图标，文字「需要关注」及异常数量 |
| `critical` | 至少一个检查达到严重条件 | 危险色图标，文字「严重异常」及异常数量 |
| `unknown` | 关键数据尚未就绪、采集失败或没有可用于判断的检查 | 中性状态图标，文字「状态未知」及原因 |

状态优先级：`critical > warning > unknown > healthy`。整体状态只聚合适用的检查项。可选硬件能力不受支持时标记为不适用，不应单独降低整体状态；已启用且本应可用的检查发生采集失败时，必须标记为 `unknown`，不能当作正常。

### 3.4 GoDesk 连接状态与主机健康状态分离

浏览器通过健康状态 API 的请求结果判断 GoDesk API 连接状态。该状态由前端维护，不属于主机健康 API 的 `overall`：

- `connecting`：尚未取得首次成功响应。
- `connected`：最近一次请求成功。
- `disconnected`：连续请求失败或超过数据新鲜度期限，无法确认当前连接。

建议底栏健康摘要每 5 秒请求一次；连续 3 次失败或超过 15 秒没有成功响应后，显示连接中断。首次请求和短暂失败期间应避免闪烁。连接中断只表示浏览器暂时无法取得 GoDesk 状态，不代表 Linux 主机已经关机或故障。

## 4. 检查维度与默认规则

检查项分为必需基础检查、可选硬件检查和后续扩展检查。阈值是首版建议默认值，最终应集中配置，禁止散落在前端组件中。

### 4.1 首版基础检查（P0）

| 检查项 | 检查内容 | 默认警告 | 默认严重 | 说明 |
| --- | --- | --- | --- | --- |
| CPU | 总体使用率、逻辑核心数 | 使用率 ≥ 85%，持续 5 分钟 | 使用率 ≥ 95%，持续 5 分钟 | 使用连续采样判断，避免瞬时峰值告警 |
| 内存 | 可用内存比例、已用/总量 | 可用比例 ≤ 15%，持续 2 分钟 | 可用比例 ≤ 5%，持续 2 分钟 | 健康判断优先使用 Linux 可用内存，不仅看缓存计入后的已用比例 |
| 存储 | 文件系统容量使用率 | ≥ 85% | ≥ 95% | 按挂载点分别检查；排除伪文件系统和只读镜像 |
| 存储 inode | inode 使用率 | ≥ 85% | ≥ 95% | 文件系统提供 inode 指标时检查；不支持时标记不适用 |
| 网络接口 | 默认路由接口的链路状态与地址 | 默认接口不可用时警告 | 默认接口明确断链时严重 | 不以流量为零判定故障；不默认要求互联网可达 |

CPU 和内存阈值采用持续时间判断。存储阈值可以在连续两次有效采样满足条件后生效。恢复阈值应设置迟滞，避免在临界值附近反复切换：

- CPU：严重状态降至低于 90% 后可降为警告；警告状态降至低于 80% 后恢复正常。
- 内存：严重状态的可用比例恢复至高于 10% 后可降为警告；警告状态恢复至高于 20% 后恢复正常。
- 存储：严重状态降至低于 90% 后可降为警告；警告状态降至低于 80% 后恢复正常。

实际实现应同时考虑持续时间和连续有效样本，采集失败时暂停阈值状态迁移。

网络默认只判断被管理主机自身的网络接口。默认路由接口优先作为管理网络检查对象；没有默认路由时，不应擅自推断主机必须连接互联网。网关连通性和外网连通性属于可配置探测，默认关闭，且必须区分网关不可达与外网不可达。

### 4.2 可选硬件检查（P1）

| 检查项 | 数据来源 | 判定规则 |
| --- | --- | --- |
| CPU / SoC 温度 | 优先读取 Linux `/sys/class/hwmon/` 与 `/sys/class/thermal/` | 优先使用传感器或内核暴露的阈值；没有可信阈值时只展示温度，不自动告警 |
| Swap | Linux 内存统计 | 展示使用量；健康判断需结合换入/换出活动，不仅凭已用比例判定 |
| Load Average | Linux 系统负载 | 展示 1、5、15 分钟值，并结合逻辑核心数解释，不以单一固定数值适配所有设备 |
| Uptime | Linux 系统运行时间 | 仅作为信息展示，不参与整体健康评分 |

温度传感器名称、单位和阈值因 x86、ARM SoC、虚拟机和嵌入式板卡而异。无法读取、没有阈值或平台不支持时应明确显示「不可用」或「仅供参考」，不得伪造温度，也不得统一套用不适合所有芯片的固定温度线。

### 4.3 后续扩展（P2）

- 用户主动选择的 systemd / OpenRC 服务健康检查。
- 用户配置的网关或指定目标连通性检查。
- 用户自定义阈值、检查启停与关注对象。
- Docker 容器等可选运行时检查。

服务检查必须通过现有服务管理抽象适配，不得将 systemd 作为所有平台的唯一前提。未被用户选为关注对象的服务不参与整体健康状态。

## 5. 数据采集与架构约束

- 复用现有 `backend/internal/monitor` 采集器；同一指标只采集一次，健康引擎消费采集快照，不再自行重复读取 CPU、内存、磁盘和网络计数器。
- 健康规则聚合独立于采集器，建议放在 `backend/internal/health`。采集层负责事实数据，健康层负责阈值、持续时间、迟滞和状态聚合。
- 指标基础采样维持约 1 秒。CPU 持续判断需要足够的有界历史窗口；温度可按约 5 秒采样。不得因底栏轮询而触发额外硬件扫描。
- 健康状态 API 返回轻量摘要，不返回系统监控的 60 点历史序列。系统监控继续使用现有 metrics API 获取详细数据。
- 首版状态与异常持续时间保存在进程内存中；服务重启后重新采集、重新判定，不承诺历史告警持久化。
- 单项采集失败应隔离处理，不应导致其他维度全部不可用。
- 对磁盘检查必须过滤伪文件系统、容器叠加层、临时文件系统和只读镜像，并保留根分区及真实数据挂载点。去重策略应避免同一设备的多个绑定挂载重复告警。

## 6. API 契约

健康状态接口目标为：

`GET /api/v1/system/status`

完整字段、状态枚举、响应示例和错误语义以 [系统监控与主机健康 API 契约](../system-monitoring.md#主机健康状态接口目标契约) 为准。接口要求：

- 必须经过现有操作者会话认证。
- JSON 响应，设置 `Cache-Control: no-store`。
- 建议由后端每秒或按采集周期更新内部快照；浏览器底栏每 5 秒读取一次。
- 返回整体状态、主机信息、检查摘要、逐项检查结果和采集时间。
- 检查项的 `unknown` 与不适用状态必须可区分。
- 该接口只读，不触发服务操作、网络配置变更或其他特权动作。

## 7. 安全、权限与兼容性

- 首版只读取运行环境可访问的系统指标和只读 sysfs/procfs 信息，不因健康检查自动提权。
- 权限不足应产生可解释的未知状态或字段不可用，不应通过隐式 sudo、NOPASSWD 或后台提权绕过现有权限模型。
- 不读取或上传与健康判断无关的用户文件、命令历史或敏感业务数据。
- 在 WSL 中展示的是 GoDesk 所在 Linux 发行版的资源，不代表 Windows 宿主机资源。
- 温度、inode、Swap、路由信息等能力按平台检测；缺失能力应优雅降级。
- 健康 API 只服务当前 GoDesk 单机实例，不引入远程采集 Agent 或额外数据库依赖。

## 8. 验收标准

1. 底栏保留开始入口、应用切换和时钟，系统状态入口表达 GoDesk 所管理主机的健康状态。
2. 底栏不再显示浏览器设备的 Wi-Fi、音量或电池状态。
3. 底栏不常驻展示多个资源百分比；点击后可以查看整体状态、异常原因和检查时间。
4. 浏览器无法连接 GoDesk 时显示连接中断，不将其解释为主机已关机。
5. 健康状态至少支持 `healthy`、`warning`、`critical`、`unknown` 四种状态。
6. 采集失败不会被当作正常；不支持的可选硬件能力不会单独造成告警。
7. CPU、内存和磁盘阈值支持持续判断与恢复迟滞。
8. 网络流量为零不会自动触发网络故障；互联网连通性不作为默认健康条件。
9. 底栏与系统监控复用同一份后端指标快照，健康状态 API 不传输历史序列。
10. 窄屏、键盘操作、读屏名称和浅色/深色主题均有明确的可访问行为。

## 9. 实施分期

| 阶段 | 交付内容 |
| --- | --- |
| V1 | CPU、内存、磁盘、网络接口与 GoDesk 连接状态；健康引擎；健康状态 API；底栏状态入口和摘要面板 |
| V2 | 温度、Swap、Load Average、Uptime、可选网关探测；补充平台兼容性 |
| V3 | 服务关注列表、自定义阈值、检查项配置和通知扩展 |

本 Spec 约束产品职责与接口边界。实现时如需调整阈值、字段或平台行为，应同步更新本 Spec 与系统监控契约。
