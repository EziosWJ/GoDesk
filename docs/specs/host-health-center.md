## 1. 背景与目标

GoDesk 是面向 Linux 主机的 Web 运维桌面。桌面底栏不应复刻 Windows 系统托盘，也不应成为一组缩小的资源仪表盘。它应提供主机健康感知入口，让操作者无需打开系统监控应用，就能判断主机是否存在需要关注的问题。

Host Health Center（主机健康状态中心）负责回答：

1. GoDesk 当前是否仍能连接到被管理主机？
2. 主机整体健康状态如何？
3. 哪些检查项异常，异常持续了多久？
4. 应该进入哪个应用查看详细信息？

核心原则：**底栏展示健康状态，健康中心解释问题，系统监控提供详细指标，服务管理负责服务操作。**

## 2. 产品范围

### 2.1 目标

- 在桌面底栏提供始终可见、低干扰的主机健康状态入口。
- 将 CPU、内存、存储、网络和温度等检查统一聚合为健康状态。
- 区分正常、警告、严重和未知，避免把采集失败或不支持误判为正常。
- 复用现有系统监控采集能力，避免重复采集同一指标。
- 提供稳定、轻量、可扩展的健康状态 API 契约。
- 在不具备传感器或特定系统能力的平台上优雅降级。

### 2.2 非目标

首版不包含：

- 完整监控大屏、长期指标存储、历史趋势报表。
- 邮件、短信、Webhook、桌面推送等通知渠道。
- 自动重启服务、自动清理磁盘或其他自动修复动作。
- 默认探测公共互联网或依赖第三方服务判断主机健康。
- 默认监控主机上的全部 systemd、OpenRC 或 Docker 服务。
- 远程多主机汇聚与集中监控。
- 将浏览器所在设备的电池、音量或 Wi-Fi 状态作为被管理主机状态。

## 3. 信息架构与交互

### 3.1 桌面底栏

底栏继续保留现有应用切换区和时钟。右侧状态区域由主机健康入口替代浏览器网络、Web Audio 音量和浏览器电池控件；托盘控件已移除。

常驻内容：

- 主机健康图标与状态文字：正常、警告、严重或未知。
- 存在警告或严重问题时，显示异常数量。
- GoDesk 连接中断时，显示独立的连接状态，不伪装成主机健康结论。
- 本地化时间与日期。

底栏不常驻显示 CPU、内存、磁盘、温度等具体数值。它们属于健康中心和系统监控的详情内容。不得使用 `navigator.onLine`、Web Audio API 或 `navigator.getBattery()` 代替 Linux 主机指标。

### 3.2 健康状态面板

点击底栏主机状态入口，打开轻量面板。面板按以下顺序组织：

1. 整体健康状态、异常数量和最近检查时间。
2. 警告与严重检查项，优先显示异常原因、当前值、生效阈值和异常开始时间。
3. 检查维度摘要。V1 展示 CPU、内存、存储、网络；V2 增加温度等已有维度。
4. 可用时显示主机名、运行时间和平台信息。
5. 提供进入「系统监控」查看详细指标的入口。

面板中的阈值必须来自健康 API 返回的生效值，前端不得复制或硬编码默认阈值。正常状态下不需要展示大段空白告警列表；可以收起正常检查项，只保留维度摘要。未知状态必须说明是尚未就绪、采集失败、数据过期还是平台不支持，不能显示成正常。`applicable=false` 的检查项应与异常项分开展示，不能计入异常数量。

面板复用现有任务栏弹出层交互：

- 点击或键盘激活入口后聚焦面板；Escape、再次激活入口或点击面板外部关闭，并将焦点返回入口。
- 面板为非模态区域，不锁定页面其他部分；打开时若焦点移出面板和入口，按现有弹出层规则关闭。
- 状态变化通过礼貌级 live region 播报，只在整体状态或异常数量变化时播报；不得在每次 5 秒轮询时重复播报。
- 状态入口的可访问名称包含状态和异常数量，例如「主机健康：需要关注，1 项异常」；图标旁的数量若已包含在名称中，应避免被读屏重复播报。
- 状态不能只靠颜色表达；图标、文字和语义色同时使用，对比度遵守 [07 交互规范](../../frontend/docs/ui-design/07-interaction-guidelines.md)。

状态入口始终可触达，不得通过缩小命中区换取空间；窄屏下的面板尺寸、滚动和回流行为见 [08 响应式规范](../../frontend/docs/ui-design/08-responsive-guidelines.md)。

### 3.3 状态语义

| 状态 | 含义 | 展示建议 |
| --- | --- | --- |
| `healthy` | 所有适用且已启用的检查均正常 | 中性图标或成功状态，文字「主机正常」 |
| `warning` | 至少一个检查达到警告条件，且没有严重项 | 警告色图标，文字「需要关注」及异常数量 |
| `critical` | 至少一个检查达到严重条件 | 危险色图标，文字「严重异常」及异常数量 |
| `unknown` | 关键数据尚未就绪、采集失败、数据过期或没有可用于判断的检查 | 中性状态图标，文字「状态未知」及原因 |

状态优先级：`critical > warning > unknown > healthy`。整体状态只聚合 `applicable=true` 的检查项，由后端计算，前端不得自行重算。

- 可选硬件能力不受支持时标记为不适用（`applicable=false`），不参与整体状态，也不计入异常数量。
- 已启用且本应可用的检查发生采集失败、数据过期或尚未就绪时，必须标记为 `unknown`，不能当作正常。
- 当警告与未知同时存在时，整体状态为警告，但未知项仍必须在面板和计数中可见。
- 每项检查的机器可读原因（`reason`）和状态映射见系统监控契约；面板文案不得依赖 `reason` 的展示名称。
- 未知状态必须区分原因：`initializing`（尚未就绪）、`collect_failed`（采集失败）、`stale`（数据过期）、`not_supported` / `no_threshold` / `no_default_route`（不适用）。

### 3.4 GoDesk 连接状态与主机健康状态分离

浏览器通过健康状态 API 的请求结果判断 GoDesk API 连接状态。该状态由前端维护，不属于主机健康 API 的 `overall`：

- `connecting`：尚未取得首次成功响应。
- `connected`：最近一次请求成功。
- `disconnected`：连续请求失败或超过数据新鲜度期限，无法确认当前连接。

轮询与展示规则：

- 底栏健康摘要每 5 秒请求一次；页面不可见时暂停轮询，恢复可见或窗口重新聚焦时立即刷新一次。
- 同一时间只允许一个未完成请求；新请求前取消或忽略过期响应，避免慢响应覆盖新状态。
- 页面可见时，连续 3 次失败或超过 15 秒没有成功响应后，显示连接中断。首次请求和短暂失败期间保持 `connecting` 或上一次状态，避免闪烁。
- 连接恢复后立即刷新，并在取得成功响应后回到 `connected`；不得要求用户手动刷新。
- 浏览器 `online` / `offline` 事件只能用于触发立即重试或提示，不得用于推断主机健康状态。
- API 请求成功但响应顶层 `stale=true`（`generatedAt` 落后超过 15 秒）时，底栏和面板按「状态未知 / 数据未更新」展示，不得显示 `healthy`；连接状态仍为 `connected`，不得把旧快照解释为主机离线。
- 连接中断只表示浏览器暂时无法取得 GoDesk 状态，不代表 Linux 主机已经关机或故障。

## 4. 检查维度与默认规则

检查项分为必需基础检查、可选硬件检查和后续扩展检查。阈值是首版默认值，集中在后端健康层配置，禁止散落在前端组件中。API 返回实际生效的阈值用于展示；恢复阈值和持续窗口只由后端使用，不通过 API 暴露。

所有 P0 阈值统一为「数值越大越差」，并作用于检查项的 `value`：

- CPU 的 `value` 是总体使用率。
- 内存的 `value` 是已用比例 `100 - available/total`；可用比例 ≤ 15% 等价于已用比例 ≥ 85%。
- 存储的 `value` 是当前触发维度（容量或 inode）的使用率。

### 4.1 首版基础检查（P0）

| 检查项 | 检查内容 | 默认警告 | 默认严重 | 说明 |
| --- | --- | --- | --- | --- |
| CPU | 总体使用率、逻辑核心数 | 使用率 ≥ 85%，持续 5 分钟 | 使用率 ≥ 95%，持续 5 分钟 | 使用连续有效采样判断，避免瞬时峰值告警 |
| 内存 | 可用内存比例、已用/总量 | 已用比例 ≥ 85%（可用 ≤ 15%），持续 2 分钟 | 已用比例 ≥ 95%（可用 ≤ 5%），持续 2 分钟 | 健康判断优先使用 Linux 可用内存，不仅看缓存计入后的已用比例 |
| 存储容量 | 文件系统容量使用率 | ≥ 85%，连续 2 次有效采样 | ≥ 95%，连续 2 次有效采样 | 按真实挂载点分别检查；过滤伪文件系统和只读镜像 |
| 存储 inode | inode 使用率 | ≥ 85%，连续 2 次有效采样 | ≥ 95%，连续 2 次有效采样 | 文件系统提供 inode 指标时纳入同一挂载点检查；不提供时该维度不适用 |
| 网络接口 | 默认路由接口的链路状态与地址 | 链路正常但无可用地址 | 默认接口明确断链 | 不以流量为零判定故障；不默认要求互联网可达 |

### 4.2 持续判定、迟滞与恢复

持续时间按有效样本累计，采集缺口暂停计时。缺口超过新鲜度期限（约 5 秒）时，丢弃缺口前的累计时长，恢复后重新累计；更短的缺口只暂停，不重置。

状态迁移规则：

- 进入更差状态需要满足对应持续条件：CPU 5 分钟、内存 2 分钟、存储连续 2 次有效采样。
- 恢复使用更低的恢复阈值和独立的恢复窗口，避免在临界值附近反复切换。恢复窗口默认为 CPU、内存 60 秒，存储连续 2 次有效采样。
- 恢复可以从严重直接回到正常；不要求逐级经过警告。

默认恢复阈值：

| 检查项 | 严重 → 警告 | 警告 → 正常 |
| --- | --- | --- |
| CPU | 使用率低于 90% 并持续恢复窗口 | 使用率低于 80% 并持续恢复窗口 |
| 内存 | 已用比例低于 90%（可用高于 10%）并持续恢复窗口 | 已用比例低于 80%（可用高于 20%）并持续恢复窗口 |
| 存储容量 / inode | 使用率低于 90% 并连续 2 次有效采样 | 使用率低于 80% 并连续 2 次有效采样 |

其他规则：

- 首份有效样本到达后，即使当前值超过阈值，也要等持续条件满足才进入警告或严重；此前保持 `healthy`，但面板仍显示当前值和阈值。
- 数据过期时检查项变为 `unknown`，不保留 `warning` / `critical`；数据恢复后重新评估，必要时重新累计持续时长。
- 不适用（`applicable=false`）的检查项不参与状态迁移，也不影响整体状态。
- 恢复阈值和持续窗口首版固定，自定义配置属于 V3。

### 4.3 可选检查（P1）

| 检查项 | 数据来源 | 判定规则 |
| --- | --- | --- |
| CPU / SoC 温度 | 优先读取 Linux `/sys/class/hwmon/` 与 `/sys/class/thermal/` | 优先使用传感器或内核暴露的阈值；没有可信阈值时只展示温度，不自动告警 |
| Swap | Linux 内存统计 | 展示使用量；健康判断需结合换入/换出活动，不仅凭已用比例判定 |
| Load Average | Linux 系统负载 | 展示 1、5、15 分钟值，并结合逻辑核心数解释，不以单一固定数值适配所有设备 |

主机名、架构、平台和 uptime 属于 `host` 信息，在 V1 返回，不单独作为检查项，也不参与整体状态。

温度传感器名称、单位和阈值因 x86、ARM SoC、虚拟机和嵌入式板卡而异。无法读取、没有阈值或平台不支持时应明确显示「不可用」或「仅供参考」，不得伪造温度，也不得统一套用不适合所有芯片的固定温度线。温度检查在 V2 实现；V1 不返回温度检查项。

### 4.4 后续扩展（P2）

- 用户主动选择的 systemd / OpenRC 服务健康检查。
- 用户配置的网关或指定目标连通性检查。
- 用户自定义阈值、检查启停与关注对象。
- Docker 容器等可选运行时检查。
- 多默认路由接口和更多网卡的主动健康检查。

服务检查必须通过现有服务管理抽象适配，不得将 systemd 作为所有平台的唯一前提。未被用户选为关注对象的服务不参与整体健康状态。

## 5. 数据采集与架构约束

### 5.1 单一采集源

- 复用现有 `backend/internal/monitor` 采集器；同一指标只采集一次，健康引擎消费采集快照，不再自行重复读取 CPU、内存、磁盘和网络计数器。
- 为支持健康判断，指标快照需要做加法扩展：内存可用字节、磁盘 inode 使用率、网卡链路状态和默认路由标记。字段定义见系统监控契约，已有字段语义不变。
- 采集器的进程内快照必须区分「空结果」和「采集失败」；健康引擎据此生成 `collect_failed` 而不是误判为不适用。metrics JSON 不必暴露内部错误。
- 采集层保留默认路由接口，即使链路关闭或没有可用地址，供健康引擎判定 `link_down` 和 `no_address`；其余接口维持现有过滤。
- 默认路由通过 procfs、sysfs 或 netlink 只读查询获取，不调用 shell。默认路由接口的选择规则见系统监控契约。
- 温度在 V2 约每 5 秒采集一次；不得因底栏 5 秒轮询而触发额外硬件扫描。
- 主机名、架构和平台在启动或快照组装时读取；uptime 每次快照读取一次，均不重复采集已有指标。

### 5.2 健康引擎

- 健康规则聚合独立于采集器，建议放在 `backend/internal/health`。采集层负责事实数据，健康层负责阈值、持续时间、迟滞、过期判定和状态聚合。
- 健康引擎在每个采集周期评估一次，并自行维护覆盖持续窗口的有界状态：CPU 至少 300 秒、内存至少 120 秒。metrics 的 60 点序列只用于展示，不能作为 5 分钟判定的完整历史。
- 状态 API 读取健康引擎的最新只读快照，不返回历史序列；系统监控继续使用 metrics API 获取详细数据。
- 单项采集失败、超时或数据过期只影响对应检查项，不应导致其他维度全部不可用。
- 首版状态、持续时间和 `since` 保存在进程内存中；服务重启后重新采集、重新判定，不承诺历史告警持久化。
- 健康引擎尚未产生首份快照时，状态接口返回 `503`；首份快照产生后，即使全部检查未知也返回 `200`。

### 5.3 磁盘与网络判定

- 磁盘检查必须过滤伪文件系统、容器叠加层、临时文件系统和只读镜像，并保留根分区及真实数据挂载点。具体过滤清单和同设备去重规则见系统监控契约。
- inode 与容量合并在同一挂载点检查中，取更严重的维度作为检查状态；inode 不可用时不生成额外的不适用检查项。
- V1 网络只检查默认路由接口；没有默认路由时标记为不适用，不推断为故障，也不要求互联网可达。
- 网关连通性和外网连通性属于可配置探测，默认关闭，且必须区分网关不可达与外网不可达。

## 6. API 契约

健康状态接口目标为：

`GET /api/v1/system/status`

完整字段、状态枚举、原因枚举、统计口径、检查项顺序、响应示例和错误语义以 [系统监控与主机健康 API 契约](../system-monitoring.md#主机健康状态接口) 为准。接口要求：

- 必须经过现有操作者会话认证。
- JSON 响应，设置 `Cache-Control: no-store`，无副作用。
- 返回整体状态、主机信息、检查摘要、逐项检查结果、生效阈值、新鲜度和生成时间。
- 检查项的 `unknown`、数据过期和不适用状态必须可区分；每项检查提供稳定的 `reason`。
- 顶层 `stale` 表示健康快照整体未及时更新；客户端不得在 `stale=true` 时显示 `healthy`。
- `summary` 必须满足契约中的计数不变量；`overall` 只由后端聚合。
- 不返回 CPU、内存和网络的历史序列；不提供阈值配置、通知或服务操作接口。
- `schemaVersion` 用于结构版本；客户端遇到未知版本或未知枚举值时降级展示，不得把未知当作正常。

## 7. 安全、权限与兼容性

- 首版只读取运行环境可访问的系统指标和只读 sysfs/procfs 信息，不因健康检查自动提权。
- 权限不足应产生可解释的未知状态或字段不可用，不应通过隐式 sudo、NOPASSWD 或后台提权绕过现有权限模型。
- 不读取或上传与健康判断无关的用户文件、命令历史或敏感业务数据。
- 主机名、平台和 uptime 只返回给已认证的操作者。
- 在 WSL 中展示的是 GoDesk 所在 Linux 发行版的资源，不代表 Windows 宿主机资源。
- 温度、inode、Swap、路由信息等能力按平台检测；缺失能力应优雅降级。
- 健康 API 只服务当前 GoDesk 单机实例，不引入远程采集 Agent 或额外数据库依赖。
- `GET /healthz` 继续作为无需认证的进程存活检查，与主机健康状态接口职责分离，不复用其响应。

## 8. 可访问性与响应式

- 状态入口必须可通过键盘到达，可访问名称同时包含状态与异常数量。
- 状态不能只依赖颜色；图标、文字和语义色同时表达。对比度遵守 [07 交互规范](../../frontend/docs/ui-design/07-interaction-guidelines.md)。
- 状态变化通过礼貌级 live region 播报，只在整体状态或异常数量变化时播报，不在每次轮询时重复。
- 面板打开后焦点进入面板，Escape 关闭并返回入口；外部点击关闭。焦点顺序与现有任务栏弹出层一致。
- 窄屏下先收起非必要文字，再收起次要信息，健康状态图标、开始入口、当前激活应用和时钟保持可见；不得缩小命中区。
- 面板在窄视口内限制宽度和高度并允许内部滚动，不能被任务栏或视口裁切。
- 验证 200% 文本缩放、320 CSS px 回流、短视口、触控、浅色和深色主题。

## 9. 验收标准

1. 底栏保留开始入口、应用切换和时钟，主机健康入口表达 GoDesk 所管理主机的健康状态。
2. 底栏不再显示浏览器设备的 Wi-Fi、音量或电池状态；不使用 `navigator.onLine`、Web Audio API 或 `navigator.getBattery()` 推断主机状态。
3. 底栏不常驻展示多个资源百分比；点击后可以查看整体状态、异常原因、当前值、生效阈值和检查时间。
4. 浏览器无法连接 GoDesk 时显示连接中断，不将其解释为主机已关机；连接恢复后自动刷新。
5. 健康状态支持 `healthy`、`warning`、`critical`、`unknown`，并有机器可读的 `reason` 区分未知原因。
6. 采集失败、数据过期和尚未就绪不会被当作正常；不支持的可选能力不会单独造成告警，且与异常项分开展示。
7. CPU、内存和存储阈值支持持续判断与恢复迟滞；恢复可以直接从严重回到正常。
8. 网络流量为零不会自动触发网络故障；没有默认路由不判定为故障；互联网连通性不作为默认健康条件。
9. 底栏与系统监控复用同一份后端指标快照，健康状态 API 不传输历史序列；健康引擎自行维护持续判定窗口。
10. `summary` 计数满足契约不变量；`overall` 与 `checks` 状态一致；警告与未知并存时未知项仍可见；顶层 `stale=true` 时不得显示 `healthy`。
11. 磁盘过滤、同设备去重、inode 合并和默认路由选择符合系统监控契约。
12. 窄屏、键盘操作、读屏名称与播报、200% 缩放和浅色/深色主题均有明确的可访问行为。
13. 后端测试覆盖状态机、过期、过滤、路由选择和 API 错误；前端 lint/build 通过，现有功能不受影响。

## 11. 已知取舍

- 首份有效样本到达后要等持续窗口满足才可能进入警告；GoDesk 重启后的最初几分钟可能只显示正常值和阈值，不显示持续超限告警。
- 首版不持久化告警历史，重启后 `since` 重新计时。
- V1 只检查一个默认路由接口，多宿主主机的备用链路不在健康摘要中体现。
- 容器内运行 GoDesk 时，overlay 根文件系统按契约被排除，可能出现没有可检查磁盘的情况；这是 V1 的已知限制。
- 温度阈值依赖平台暴露；没有阈值时只展示读数，不告警。
- 阈值和恢复窗口首版固定，自定义配置属于 V3。
- 不提供通知、自动修复、历史趋势或远程多主机聚合。
- 健康 API 只面向 Linux 主机；WSL 展示发行版内部资源。

## 12. 验证要求

- 后端单元测试：阈值与持续窗口、恢复迟滞、采集缺口、过期、首份样本、磁盘过滤与去重、inode 合并、默认路由选择、`summary` 不变量、`reason` 映射。
- 后端 handler 测试：`200`、`401`、`503`、`Cache-Control: no-store`、单项失败不影响其他检查、`generatedAt` 格式。
- 前端验证：5 秒轮询与可见性暂停、连接状态、数据过期提示、面板焦点与 live region、窄屏、200% 缩放、明暗主题。
- 手工矩阵：真实 systemd 主机、WSL、无默认路由、权限受限账号、inode 紧张或不可用的文件系统、多挂载点同设备。
- 命令：`go -C backend test ./...`、`pnpm --dir frontend lint`、`pnpm --dir frontend build`。

本 Spec 约束产品职责与接口边界。实现时如需调整阈值、字段或平台行为，应同步更新本 Spec 与系统监控契约。
